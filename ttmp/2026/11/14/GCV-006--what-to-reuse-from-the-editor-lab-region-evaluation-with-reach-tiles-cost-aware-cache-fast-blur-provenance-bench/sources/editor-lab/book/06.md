# Caching by content

The fastest tile is one the engine does not compute. After an edit, most tiles of most layers are what they were a moment ago; the question is how the engine knows which, and how much it can afford to remember. This chapter describes the engine's answer: name every tile by a hash of everything it was computed from, keep tiles under a memory budget, choose carefully which to drop, and let undo find old tiles by the same names. It then reads the engine's design against darktable's and against the vocabulary of build systems, measures what that design wastes, and ends with the parts of a production cache the lab does not have: checkpoints, tiers and compression. By the end you will be able to write a content key for a tile, choose its width from the birthday bound, choose an eviction policy by measuring it, place checkpoints from a cost table, and say when a cache can stop a rebuild early.

## 6.1 Keys instead of invalidation

One way to keep a cache correct is **invalidation**: when something changes, find every cached result that depended on it and throw it away. That needs a record of who depends on what, and every new feature must remember to update it. The engine uses **content keys** instead. A tile's key is a hash of everything that went into it, so a changed input gives a different key, and the stale entry is not deleted so much as never asked for again. The rule for a tile of layer <i>i</i> is:

```math
key(i, tile) = H( settings of layer i,  pixels it reads,  key(i − 1, each tile it reads) )
```

This is a **Merkle** construction: a key summarises everything below it, as a commit hash in Git does. Figure 6.1 draws the chain for three layers. Change a slider on layer 3 and the keys of layer 3 and everything above change; layers 0 to 2 keep theirs, and their tiles stay in the cache. Paint on the bottom layer and only the keys of tiles over the painted 64 px blocks change, plus, above a blur, the tiles whose aprons reach them.

`resolve` comes first: a hidden layer, or one inside a hidden group, passes its backdrop's key through and costs nothing. `below` finds that backdrop, the nearest showing layer under this one, stepping over a group's contents and never going under the floor of an isolated group, where the stack starts again from transparent. A pass-through group at full opacity without a mask is the identity (Section 2.5), so it takes the key of what its children made, `top(i)`, and shares their tiles. `lh` hashes the layer's kind, opacity, blend, params, offset and mask components. A raster layer mixes in the revisions of the 64 px blocks under the tile; a brush mask component does the same over the tile grown by its feather's reach. Then come the keys below: for a group, its backdrop's and its children's; one tile for a pointwise layer, every tile the apron touches for a layer with reach. An opaque fill hides everything under it, so its key ignores what is below. The result is memoised per frame, because the same key is asked for many times while a frame renders.

Content keys have one more property that matters later: they do not care how a state was reached. Two different edit histories that end in the same settings give the same keys, which is why undo can find old tiles (Section 6.6), and why a key computed in a worker or on another machine names the same tile.

The program below shows the chain at work on a copy of the open document. It changes the opacity of the second layer from the bottom and counts, layer by layer, the tiles whose key changed. On D-01 the Photo layer keeps all 40 keys and every layer from Warmth up changes all 40.

```run keys.js
// Change one setting of the second layer from the bottom and count, layer by layer, the tiles whose
// key changed. Keys below the edit stay; every key at and above it changes. Works on a copy.
const ws = new Workspace(cloneDoc(app.ws.doc), { tile: 128 }), e = ws.engine, g = e.grid(0);
if (ws.doc.layers.length < 2) return 'this needs a document with at least two layers';
const keys = () => ws.doc.layers.map((_, i) => {
  const out = []; for (let ty = 0; ty < g.ny; ty++) for (let tx = 0; tx < g.nx; tx++) out.push(e.key(i, 0, tx, ty)); return out;
});
const before = keys(), l = ws.doc.layers[1];
ws.setLayer(l.id, { opacity: l.opacity * 0.9 }); e.invalidate();
const after = keys();
return ws.doc.layers.map((x, i) => ({ layer: `${i} ${x.name}`, keys_changed: `${after[i].filter((k, j) => k !== before[i][j]).length} of ${g.nx * g.ny}` }));
```

## 6.2 How wide a key must be

A hash maps many inputs to few outputs, so two different tiles can share a key. When they do, the cache returns the wrong picture and nothing reports an error. How likely that is follows from the **birthday bound**: among <i>N</i> keys drawn at random from <i>2<sup>b</sup></i> values, the expected number of colliding pairs is about

```math
N² / 2^(b+1)
```

A long editing session can create a hundred thousand distinct tile keys. With 32-bit keys that gives 10¹⁰ / 8.6 × 10⁹ ≈ 1.2 expected collisions: in a long session, a wrong tile is more likely than not. The engine therefore builds its keys from two independent 32-bit hashes, keeps 32 bits of one and 20 of the other, and joins them into a 52-bit integer. The expected count becomes 10¹⁰ / 9.0 × 10¹⁵ ≈ 10⁻⁶.

Fifty-two bits is not arbitrary. A JavaScript number holds integers exactly up to <i>2<sup>53</sup></i>, and a `Map` keyed by numbers is fast. Wider keys need a `BigInt` or a string, both slower to hash and compare in a map that is consulted thousands of times a frame. An engine in WebAssembly or on the GPU has 64-bit integers and should use them. Figure 6.2 draws the bound for the three widths.

darktable, whose cache is described in Section 6.7, uses 64-bit keys made with a variant of Daniel Bernstein's djb2 string hash, which multiplies the running value by 33 and exclusive-ors in each byte of the input. The bound above assumes keys that behave as random draws. A hash as simple as djb2 was not designed to guarantee that for structured inputs such as nearby parameter values, so for such a hash the figure is the best case, not a measurement. The engine's `hmix` mixes each input word with three multiplications and three xor-shifts, in the style of the MurmurHash3 finaliser, which spreads a one-bit difference in the input across the whole output word; the exercises ask you to test that.

## 6.3 The cache and its budget

The **tile cache** maps keys to rendered tiles. A tile of 128 × 128 pixels at four 32-bit channels takes 256 KiB, so the default budget of 96 MB holds 384 of them. D-01 with all eight layers cached needs 8 × 40 = 320 tiles, 80 MB, which fits. The bench's modelled tablet has 32 MB, 128 tiles, and the modelled phone 16 MB, 64 tiles: a fifth of the stack.

The real numbers are larger. A 24-megapixel photograph at 128 px is about 1,500 tiles a layer, 384 MB a layer in 32-bit floats. No browser tab can cache a ten-layer stack of that at level 0, so a production engine caches selectively (Section 6.5), keeps coarser levels, which are cheap, and stores tiles in fewer bits (Section 6.9).

Desktop engines set their budgets from the machine. GEGL, the engine under GIMP, defaults its tile cache to the machine's total memory, reduced to what is available and never below 512 MB; GIMP's own preferences can set it. Krita's defaults allow its tiles up to half of physical memory, then swap to a file of up to 4 GiB. darktable budgets by **cache lines**, one rendered region each, not by bytes: 64 lines for the full pipe that draws the centre view, 12 for the preview pipe, 5 for the second window's pipe and 2 for exports and thumbnails. A browser tab has no such knowledge: `navigator.deviceMemory` reports a rounded figure in some browsers and nothing in others, and the tab can be killed for using too much, so an engine in a tab should set a budget and measure against it, as the bench's profiles do.

## 6.4 Which tile to drop

When a new tile would pass the budget, the cache must evict something. The engine offers two policies, chosen in the Bench's Engine block.

**Least recently used** (LRU) drops the tile that has gone longest without being asked for. JavaScript's `Map` keeps insertion order, which makes LRU short: on every hit, delete the entry and insert it again at the end; to evict, take from the front.

**Cost-aware** uses **GreedyDual-Size**, a policy from web caching. Each entry gets a priority <i>H = clock + cost / size</i>, where cost is the time it took to compute. Eviction removes the entry with the lowest <i>H</i> and moves the clock up to that value, so entries that are never used again are eventually overtaken by newer ones, while expensive tiles survive longer than cheap ones of the same age.

```js
// engine.js · TileCache
{{src:TileCache.prototype.get}}
{{src:TileCache.prototype.put}}
{{src:TileCache.prototype.evict}}
```

`get` counts a miss, or a hit after renewing the entry: moving it to the end for LRU, recomputing its <i>H</i> for cost-aware. `put` records the cost in microseconds, then evicts until the total is under budget, never evicting the entry it has just added. Cost-aware eviction scans the whole map for the minimum, which is linear in the number of entries; at a few hundred entries that is microseconds, and a heap would make it logarithmic.

Undo is the clearest win: ten edits, ten undos and ten redos on the top adjustment revisit the tiles of eleven states. LRU keeps the most recently computed tiles, the top layers of the latest states, and lets the tiles below the edited layer age out, though every state shares them; it recomputed 10,560 tiles. Cost-aware ranks those shared tiles, Sharpen's above all, by what they cost to make, kept them, and recomputed 2,662, a quarter as many. A brush stroke low in the stack goes the other way: each dab revisits the tiles the last dab touched, which is the access pattern LRU is built for, while cost-aware gave up some of those cheap, recently used tiles to keep expensive old ones, and recomputed a third more. A scrub of the lowest adjustment touches every tile every update and fits neither policy: both recompute everything.

darktable's policy is a third design, built for a few large entries. Every lookup ages every line by one; a hit sets the line's age to minus the number of lines, which protects it for at least that many lookups; a new result replaces the oldest line and starts at age 0, or at minus the number of lines if the pipe marks it as important. With 64 lines of whole regions the scan costs nothing. darktable also checks that a line whose key matches has the expected buffer size, and discards it if not, a guard against the collisions of Section 6.2. GEGL evicts the least recently used tile and, when the program is idle, writes dirty tiles among the least recently used fifth of its cache to its swap file, so that evicting them later needs no write.

The lesson for an engine is to measure eviction on the workloads that matter, and to treat the policy as a setting, not a constant. The bench runs both: [compare them on the tablet](lab:bench?scenario=undo,stroke-low,toggle&profile=tablet&tile=128&preview=on&evict=lru,cost&run=1).

## 6.5 What to cache: granularity and checkpoints

This engine caches the output of every layer at every tile. That is the simplest correct design and the most memory-hungry: eight layers cost eight times one. The alternative is **checkpoints**: cache only after some layers, and recompute the layers between checkpoints from the nearest one below.

Where to put them follows from the costs. Table 6.1 gives the measured time of each layer of D-01 over a full cold render.

| layer | kind | ms, all 40 tiles |
|---|---|---|
| Photo | image | 19.9 |
| Warmth | temperature | 24.0 |
| Darker sky | exposure, linear mask | 32.0 |
| Sun glow | exposure, radial mask | 32.6 |
| Contrast | curves | 16.8 |
| Sharpen | unsharp mask, reach | 87.1 |
| Vignette | vignette | 28.2 |
| Paint | paint | 18.9 |

**Table 6.1.** Time spent in each layer during a cold render of D-01 at 128 px tiles, one run.

Sharpen costs more than the three layers below it together, and it is the only layer with reach. A checkpoint after Sharpen means a scrub of Vignette never recomputes it; a checkpoint before it means a scrub of Sharpen itself starts from cached input. The pointwise layers between checkpoints cost 17 to 33 ms a frame each and can run as one fused pass ([Chapter 8](lab:book?ch=8)), which on a GPU is often cheaper than reading their cached outputs back. A cache with checkpoints after Photo, before Sharpen, after Sharpen and at the top holds four tiles per position instead of eight, 40 MB for D-01 instead of 80.

Granularity has a second axis: what a key covers. This engine keys per tile per layer. A coarser key (per layer, for the whole picture) is cheaper to compute and useless for local edits; a finer one (per 64 px block inside a 256 px tile) saves work on small strokes and costs more key computation. Key computation is not free: D-01 at 64 px tiles computes 1,200 layer keys per frame, each hashing a dozen numbers and looking up a memo, 1.3 ms in all on the machine that built this book, against 0.2 ms for the 320 keys at 128 px.

## 6.6 Undo meets the cache

History in this workbench stores **commands**, not pictures: a slider change records the layer's settings before and after; a brush stroke records, for each 64 px block it touched, a copy of the block before and after. Undoing a setting puts the old settings back. Its keys are then the old keys, and if those tiles are still in the cache, undo renders with no tiles computed at all. That is what the undo scenario measures, and why eviction policy matters so much there.

A brush stroke's undo is the same idea at block granularity. Restoring the old bytes of each touched block restores its content, but the revision number goes up, so the key is new and the tile is recomputed. A design that hashed the pixels of each block would find the old tiles again, at the price of hashing every touched block on every stroke: 64 × 64 × 4 bytes, 16 KiB a block.

## 6.7 A vocabulary from build systems

A cache of rendered tiles is a build system. Its tasks (one layer at one tile) have inputs (settings, pixels, the tiles below) and an output, and the cache needs a rule for deciding when a stored output can be reused. Mokhov, Mitchell and Peyton Jones classify these rules, which they call **rebuilders**, in *Build Systems à la Carte*, using real build systems as examples.

- **Dirty bits.** Mark what changed and everything that depends on it, and rebuild the marked tasks. Make, with file times standing in for the bit, and Excel work this way. In Section 6.1's terms this is invalidation.
- **Verifying traces.** Record, for each task, a hash of every input it read and of its output. To decide whether to rebuild, hash the current inputs and compare. Shake works this way.
- **Constructive traces.** Record the same and keep the output too, keyed by the input hashes, so a matching trace supplies the output without running the task. This is what a shared cloud cache needs; Bazel works this way.
- **Deep constructive traces.** Key each output by the hashes of the terminal inputs, the sources at the bottom of the graph, instead of by its immediate inputs. Buck and Nix work this way. A lookup needs no intermediate value: the key exists before anything has been built.

This engine's key is a deep constructive trace. A tile's key hashes the layer's settings, its own pixel revisions and the keys of the tiles below, which were made the same way all the way down, so no pixel value ever enters a key. darktable arrived at the same design. Its pixelpipe cache key starts from the image id, the pipe type and the colour profiles, then chains in the hash of each enabled module's parameters up to the module's position, and finally the region of interest when there is one. Both engines chose it for the same reason: the key can be computed before any work, so the scheduler can ask the cache about a whole column of the stack at once and compute only what is missing.

The paper names the price. A deep constructive trace cannot support **early cutoff**: the case where a task is rebuilt, its output turns out to be what it was, and the tasks that depend on it are therefore not rebuilt. When keys are made from keys, a changed input changes every key above it, whether or not a single pixel changed.

## 6.8 Early cutoff, measured

How much does that cost on a real stack? Table 6.2 changes one setting on each of four layers of D-01 and compares that layer's 40 output tiles before and after, bit for bit.

| layer and change | output tiles unchanged | layers above | tile computations an early cutoff would skip |
|---|---|---|---|
| Darker sky, exposure −1 EV | 16 of 40 | 5 | 80 of 240, 33 % |
| Sun glow, exposure +0.8 EV | 26 of 40 | 4 | 104 of 200, 52 % |
| Vignette, amount −0.6 | 8 of 40 | 1 | 8 of 80, 10 % |
| Contrast, contrast 0.5 | 0 of 40 | 3 | 0 of 160 |

**Table 6.2.** Output tiles of one layer that are bit-identical after a setting changes, on D-01 at 128 px tiles, and the work an early cutoff would save in the layers above. Measured by `test/cutoff.js` and by the program below; the counts are the same on every machine.

The unchanged tiles are where the layer has no effect. Darker sky's linear mask is zero over the lower part of the picture, Sun glow's radial mask is zero outside its ellipse, and the vignette leaves the middle of the frame alone. A global layer such as Contrast changes every tile. Masked adjustments are the common case in real edits, so the waste is large where it matters: after an edit of a masked layer, a third to a half of the engine's work recomputes tiles whose inputs are, pixel for pixel, what they were.

```run cutoff.js
// Early cutoff on D-01: after one setting changes, how many of that layer's output tiles are
// bit-identical to before? Every one of them is work a cache keyed by output could skip above it.
if (app.ws.doc.code !== 'D-01') return 'load D-01 first, from the scene menu or Chapter 6';
const cases = [['Darker sky', { ev: -1 }], ['Sun glow', { ev: 0.8 }], ['Vignette', { amount: -0.6 }], ['Contrast', { contrast: 0.5 }]];
return cases.map(([name, params]) => {
  const ws = new Workspace(cloneDoc(app.ws.doc), { tile: 128, budgetMB: 512 }), e = ws.engine, g = e.grid(0);
  const l = ws.doc.layers.find(x => x.name === name), i = ws.doc.layers.indexOf(l), above = ws.doc.layers.length - 1 - i;
  const out = () => { const t = []; for (let ty = 0; ty < g.ny; ty++) for (let tx = 0; tx < g.nx; tx++) t.push(e.tile(i, 0, tx, ty).buf.slice()); return t; };
  const a = out(); ws.setLayer(l.id, { params }); e.invalidate(); const b = out();
  const same = a.filter((t, k) => t.length === b[k].length && t.every((v, j) => v === b[k][j])).length;
  return { layer: name, change: JSON.stringify(params), tiles_unchanged: `${same} of ${a.length}`, avoidable: `${same * above} of ${a.length * (above + 1)} tile computations` };
});
```

There are two ways to win the work back.

- **Static: identity tiles.** Where a layer's mask is zero over a whole tile, the layer is the identity there, and its key can pass the key of the tile below straight through, as a hidden layer's does (Section 6.1). That needs a conservative bound for each mask component, such as the rectangle outside which a linear or radial component is zero, at the cost of one rectangle test per tile. The keys stay deep constructive traces and can still be computed before any work.
- **Dynamic: verifying traces.** Hash each output tile as it is computed, and build the keys above from those output hashes. Then any layer whose output did not change stops the rebuild, whatever the reason. The cost is hashing every computed tile: on the machine that built this book, a 32-bit hash of a 128 px float tile (256 KiB) took 0.093 ms, 2.7 GB/s, and a pointwise layer's tile costs 0.42 to 0.60 ms (Table 6.1 divided by 40), so hashing adds 15 to 22 % to the cheapest layers and less to the rest. And a key can no longer be known before the tiles below it exist, so the scheduler loses its look-ahead.

The static fix recovers the masked rows of Table 6.2 almost for free. The dynamic one also catches changes that have no effect for other reasons (a highlight that was already clipped pushed further, a curve edited where the picture has no values) and costs time on every tile.

> **Careful.** A cutoff on bit-identical output is exact. A cutoff on output that is "nearly the same", within a tolerance, is another thing: differences under the tolerance can add up across layers and across edits, and the picture would then depend on the order of edits that produced it, losing the property of Section 6.1 that the same state gives the same picture.

> **Exercise.** For each mask component kind of [Chapter 3](lab:book?ch=3), write the rectangle outside which it is zero, or say why there is none. Which kinds can never give an identity tile?

## 6.9 Tiers and compression

A browser tab has more places to keep a tile than its JavaScript heap, at different costs.

- **GPU memory.** Fastest to composite and display from, and the only place a GPU engine's tiles should normally live. Reading a tile back to the CPU costs a copy and a wait ([Chapter 8](lab:book?ch=8)).
- **CPU memory.** The lab's only tier. Typed arrays outside the JavaScript heap, transferable to workers without copying.
- **Disk.** IndexedDB or the origin private file system can keep tiles across sessions, so a reopened document shows its last state without a cold render. Reads typically take milliseconds, so this tier suits the pyramid and the final composite, not intermediate layers.

Photoshop on the web shows how far the disk tier can go. Its engine keeps image data in a virtual-memory system of its own, with **scratch files** in the origin private file system as the backing store for its pages, because on other platforms it would map files into memory with `mmap`, which the web could not do with good performance until the file system's synchronous access handles arrived. A tile there is a square region of one layer that occupies one or more pages. When Photoshop processes pixels it iterates over tiles, and the virtual-memory layer makes sure each calculation's source and destination tiles are in memory, reading them from scratch files when needed and writing other pages out to make room. The data is kept as a mipmap pyramid of tiles, so zooming out reads a coarse level. The same mechanism is how it edits documents larger than the 4 GiB address space of 32-bit WebAssembly ([Chapter 8](lab:book?ch=8)). GEGL and Krita do the same on the desktop with swap files, and GEGL's idle washing (Section 6.4) is the policy that keeps that tier cheap to evict into.

Compression multiplies what each tier holds. A tile in 16-bit half floats takes half the memory of 32-bit floats and keeps about three decimal digits, enough for any intermediate that will be shown in 8 bits; 8 bits per channel takes a quarter, but loses precision that later layers (a strong curve, a large exposure change) would expose as banding. A common split keeps intermediates in 16 bits and the displayed composite in 8.

Each of these is a measured trade, and none is in the lab. The exercises ask you to add one.

## Toward a reusable API

```text
key(layer i, L, tx, ty) → 52-bit integer      hash of settings, pixel revisions and the keys of the tiles read below
passThrough(layer, L, tile) → boolean          true where the layer is the identity: hidden, zero opacity, or zero mask
cache.get(key) → tile | null                   counts a hit or a miss and renews the entry for its policy
cache.put(key, tile, costMs)                   stores, then evicts until under budget, never the entry just stored
cache.policy ∈ { lru, cost }                   least recently used, or GreedyDual-Size with H = clock + cost / size
cache.budget(bytes) · cache.stats()            the budget, and hits, misses, evictions and peak bytes for the bench
checkpoint(layer) → boolean                    whether outputs of this layer are kept; layers between are recomputed
outputHash(tile) → 32-bit integer              the verifying-trace alternative: keys above built from output hashes
```

## Key points

- A content key hashes a tile's settings, the pixels it reads and the keys of the tiles under it, so a changed input gives a new key and the same state gives the same key however it was reached.
- Keys must be wide: 32 bits give an expected collision in a session of 10⁵ keys, while 52 bits fit a JavaScript number and make collisions negligible, provided the hash mixes well.
- A 128 px float tile costs 256 KiB and a 24-megapixel layer 384 MB, so production engines budget their caches and cache selectively.
- LRU suits strokes and cost-aware eviction suits undo and toggling, so an engine should measure both on its own workloads and keep the policy a setting.
- Checkpoints before and after expensive layers keep most of the benefit for a fraction of the memory.
- In the vocabulary of build systems this engine and darktable use deep constructive traces, which can be looked up before any work but cannot cut a rebuild off early.
- On D-01, edits of masked layers leave 16 to 26 of 40 output tiles bit-identical, so up to half the work after an edit is avoidable; zero-mask pass-through recovers it statically, output hashes at about 0.1 ms a tile recover it dynamically.
- GPU, CPU and disk tiers and 16-bit storage extend the cache, and Photoshop on the web shows that a disk tier in the origin private file system can carry documents larger than WebAssembly's address space.

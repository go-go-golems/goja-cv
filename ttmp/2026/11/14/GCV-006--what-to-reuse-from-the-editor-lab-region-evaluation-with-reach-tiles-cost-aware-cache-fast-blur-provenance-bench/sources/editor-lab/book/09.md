# Designing a fast engine

The previous chapters took the engine apart one mechanism at a time. This one puts the mechanisms back together as a design for a production photo engine in the browser: what it must achieve, stated as numbers; the parts it needs and how they connect; and an order in which to build it so that every step can be measured. Before the parts, it sets the choices of eight production systems side by side, because where they agree is the best evidence of what a fast engine needs. The lab is a working prototype of the first half of the build order, and the chapter says where it stops. By the end you will be able to write an engine's requirements as numbers, defend each part of the design from a measurement or from a production system that made the same choice, and plan the build so that every step ends with a number.

## 9.1 Requirements as numbers

"Fast" is not a requirement. A requirement names an event, a measure and a limit, so that a bench can say pass or fail. Table 9.1 is a set to start from; the limits come from the frame budget of [Chapter 7](lab:book?ch=7) and are meant to be argued with, not copied.

| event | measure | limit |
|---|---|---|
| any input, during any work | overlay and cursor update | every frame: 16.7 ms at 60 Hz |
| a slider or brush gesture | preview update, p95 | 16.7 ms |
| the end of a gesture | settle to full resolution, p95 | 250 ms for the visible area |
| undo or redo of the last ten steps | update, p95 | 16.7 ms when the tiles are cached |
| opening a 24 MP document of ten layers | first preview · full view | 500 ms · 2 s |
| any state | memory | the device class's budget, measured |
| any kernel on the GPU or in WebAssembly | difference from the reference | 0.5 of an 8-bit step |
| any preview | difference from the final render | stated per layer kind (Table 5.3) |

**Table 9.1.** Example requirements for an editing engine. Each is something the bench can measure.

Measured against this table, the lab passes some rows on D-01 and fails others, on the machine that built this book. Scrubbing the top adjustment with previews on has a p95 of 5.9 ms and passes. Scrubbing the lowest adjustment has a preview p95 of 28 ms in one run and 17 ms in another, and fails both times, and its settle, 282 to 287 ms, misses 250 ms. The spread between those runs is the reason Chapter 7 asks for repeats: the gate decision was the same, the margin was not. Those two failures are the specification for the rest of this chapter: the lab's preview is too slow when everything above it must be recomputed, and refinement on one thread is too slow for the whole stack.

## 9.2 What production engines chose

Chapters 5 to 8 read the source code and the published accounts of several systems. Table 9.2 puts their main choices side by side, in the terms of this book.

| system | unit of work | how results are named | coarse path | where code runs | how work is abandoned |
|---|---|---|---|---|---|
| this lab | 64 to 256 px tiles, per layer | 52-bit content keys built from keys below | whole-stack previews at pyramid levels 1 to 3 | JavaScript; WebAssembly and WebGPU as probes | generation check between tiles |
| darktable | one module over a region; tiles when memory is short | 64-bit chained hash of image, profiles and module parameters | a separate preview pipe with its own cache | C with OpenMP; OpenCL | atomic flag checked between modules; runs younger than half the average finish |
| GIMP and GEGL | 128 px GEGL tiles; projection chunks sized to fill 1/15 s | buffers own their tiles; changed regions are redrawn | not covered here | GEGL operations on CPU threads | stops between chunks |
| Krita | 64 px tiles | changed regions are redrawn | Instant Preview strokes on a smaller canvas | CPU threads; an OpenGL canvas | the full stroke is recomputed from its start |
| libvips | regions pulled by a sink | an operation cache keyed by operation and arguments | Deep Zoom pyramids written to files | threads with a copy of the pipeline's state; Highway SIMD | not covered here |
| Photoshop on the web | square tiles of one layer, in virtual-memory pages | not documented | a mipmap pyramid of tiles; cache levels on the desktop | C++ through Emscripten, threads, Halide kernels with SIMD | not covered here |
| Figma | not covered here | not covered here | not covered here | C++ through Emscripten; WebGPU with a WebGL fallback | switches to WebGL during a session on failure |
| Chromium cc | about 256 px in software; viewport width × ¼ height on the GPU | tiles replaced when their content is invalidated | a pending tree is rasterised while the active tree is drawn | raster worker threads; GPU raster | running tasks finish; unstarted ones are left out of the next task graph |

**Table 9.2.** The choices of eight systems, from the sources read for Chapters 5 to 8. "Not covered here" marks what those sources did not say, not what the system lacks.

Four things every system in the table does, whatever else differs:

- **It cuts work into rectangles or chunks.** Nothing renders a whole picture as one unit while the person is working. The sizes cluster between 32 and 256 px, and the one system that adapts its unit, GIMP, adapts it in time, not in pixels.
- **It has a coarse path separate from the full one.** darktable's preview pipe, Krita's Instant Preview, Photoshop's cache levels and Chromium's pending and active trees all keep something cheap on screen while the expensive result is made.
- **It abandons work only between units.** A module, a raster task, a tile or a chunk always runs to its end; the systems differ only in how they decide not to start the next one.
- **It keeps a slower path that always works.** Chromium switches from GPU to software raster when the GPU process has crashed too often; Figma falls back from WebGPU to WebGL during a session; this lab keeps a JavaScript reference for every kernel.

And two things they disagree on, which an engine must decide for itself:

- **Names or invalidation.** The lab, darktable and libvips name results by what they were computed from; Chromium, Krita and GIMP redraw the regions that were marked as changed. Names cost a key per tile and make undo, toggling and work on other threads find old results ([Chapter 6](lab:book?ch=6)). Invalidation costs nothing per tile and must be told about every change. An engine in a browser, with workers and a long history, has more to gain from names.
- **Fixed or adaptive steps.** GIMP's chunks fill an interval and overshoot when the cost changes; the lab's tiles never overshoot by more than one tile but pay a fixed cost per tile ([Chapter 7](lab:book?ch=7)). With a cache keyed by tile, the step must be the tile, and what adapts is the number of tiles per slice.

## 9.4 The document model

The lab's document is mutable: an edit changes a layer in place and bumps revision counters, and history stores commands. That works with one thread. With several, the renderer must read a consistent state while the person keeps editing, and the simplest way to guarantee it is **immutable versions**: every edit produces a new document value that shares everything it did not change with the previous one. A slider change makes a new layer object and a new layer list; every other layer, and every raster, is shared. A brush stroke makes new 64 px blocks for the blocks it touched and shares the rest, which is the copy-on-write the lab's history already does.

Versions make three things easy. A worker or the GPU can render version 41 while the UI produces version 42, with no locks. History is a list of versions, so undo is a pointer move. And content keys ([Chapter 6](lab:book?ch=6)) can be computed from a version alone, so two threads that render the same version name the same tiles. The cost is allocation on every edit, which for layer settings is a few objects, and for strokes is the blocks the stroke touched.

Chromium's compositor applies the same idea to the screen. It keeps a **pending** tree, whose tiles are being rasterised, separate from the **active** tree it draws from, and activates the pending tree only once the content needed to show it is ready. The person never sees a half-rendered state; they see the old state until the new one is complete. An editing engine needs the same rule for refinement: tiles of a new version are drawn over the preview as they finish, but a version should never mix tiles of two versions in a way that shows a seam the person could mistake for an edit.

## 9.5 The render graph and its compiler

A layer stack is a chain, but an engine should treat it as a **graph** of nodes: sources, pointwise operations, neighbourhood operations with a reach, masks (each a small graph of components, [Chapter 3](lab:book?ch=3)) and blends. Each node declares what the rest of the engine needs to know about it:

- its **key** from its settings and its inputs' keys;
- its **reach** at each pyramid level;
- a **cost** estimate per pixel, refined from measurements;
- whether it is **level-invariant**, from a measured table like Table 5.3;
- its **implementations**: a JavaScript reference, and where they exist a WebAssembly kernel and a WGSL fragment.

Before each render the **compiler** turns the graph for one version into work. It fuses runs of pointwise nodes into single passes ([Chapter 8](lab:book?ch=8)), places **checkpoints** where the cache should keep results (before and after expensive nodes, Section 6.5), chooses the pyramid level for the zoom and for any preview, and expands the result into tile jobs: for each visible tile, the chain of node outputs it needs, each with its key. A job whose key is already in the cache is not a job.

Two existing systems divide the work the same way. Halide keeps a pipeline's **algorithm**, what each stage computes, separate from its **schedule**, where and in what order each stage runs and what is stored, and its compiler produces the loops from both ([Chapter 8](lab:book?ch=8)); the graph compiler here plays the schedule's part for a layer stack. libvips builds a graph of operations lazily and evaluates it on demand: each operation provides start, generate and stop functions, and a sink at the end of the pipeline pulls regions through, so a large intermediate is never computed in full when the output needs only part of it. Because its operations have no side effects, libvips can also cache calls by their arguments, which is the content key of [Chapter 6](lab:book?ch=6) at the level of whole operations.

Compiling is cheap compared with rendering and must stay so: it runs on every input event. The lab's equivalent, computing keys with a memo, took 0.2 ms for D-01's 320 keys at 128 px tiles and 1.3 ms for the 1,200 at 64 px.

## 9.6 The scheduler and executors

The scheduler receives requests (a version, a level, a set of tiles, a priority) and produces work for **executors**. It keeps the rules of [Chapter 7](lab:book?ch=7): input first, the gesture's preview next, visible tiles centre first, then neighbours and background work; only the newest version of a gesture is rendered; a job checks its generation before starting and its result enters the cache whatever the generation. It also deduplicates: two requests that need the same key wait on one job.

Each executor runs a kind of job well. The GPU executor runs fused pointwise passes, blurs, masks and blends and leaves the result resident. A pool of workers runs WebAssembly kernels for the work that is serial or data-dependent, and everything when WebGPU is missing. The JavaScript reference runs in tests, and in production only as a last fallback. The scheduler chooses by availability and by measured cost: a small job may be cheaper on the CPU than the round trip to the GPU.

## 9.7 Cache tiers

The cache is keyed by content and split by where tiles live. GPU textures hold what is being displayed and the checkpoints near it. CPU memory holds tiles that were evicted from the GPU, and everything when the engine runs without a GPU, in 16-bit floats unless a node needs more. Disk holds the pyramid of each source and the last composite, so a reopened document shows its last state at once. Each tier has a budget in bytes, its own eviction policy chosen by measurement (Figure 6.3 is the reason it is a setting), and a counter for hits, misses and evictions that the bench reads.

## 9.8 Previews and levels

The compiler chooses two levels per render. The **zoom level**, from the view's scale and the device pixel ratio (Section 5.5), is not a compromise: it is the level whose pixels the screen can show. The **preview level**, during a gesture, is chosen so that the preview fits the frame, adapting from the last preview's cost as the lab's renderer does.

Level invariance decides what a preview may contain. A layer that is far from invariant (a threshold, posterize or grain) is either rendered at the zoom level even in a preview, if it is cheap enough, or the preview is marked as approximate. The person should never take a decision on a preview that differs from the final render in a way they cannot see coming.

## 9.9 Building with the bench

An engine like this is built and kept fast by measurement, and the bench is the part of the system that does it.

- **Scenarios are tests.** Each scenario has a gate from Table 9.1. A change that makes a scenario fail its gate fails the build, as a broken unit test would.
- **Run on fixed machines.** Timings mean something only against the same machine and browser. A continuous-integration job on a dedicated machine, in headless Chrome as this book's numbers were made, gives a time series; the modelled profiles give early warnings, and real devices calibrate them.
- **Record real sessions.** Synthetic scenarios miss how people edit. The bench's recorded sessions replay real edits on a copy of the document; a library of them is the most realistic test an engine has.
- **Test parity.** Every GPU and WebAssembly kernel is compared with the reference on test pictures, with a stated tolerance, as the probes do. Every preview level is compared with the final render, as Table 5.3 does.
- **Keep the records.** Export each run with its environment. A regression found a month later is diagnosed by comparing two exported runs.

## 9.10 An order to build it in

The order below puts correctness before speed, measurement before optimisation, and the CPU before the GPU, because each later step needs the earlier ones to check it. Each milestone ends with a number.

| milestone | what it adds | done when |
|---|---|---|
| 1. Reference engine | every kind and blend mode in JavaScript, premultiplied, with tests | golden pictures match to the bit |
| 2. Tiles and keys | a tile grid, content keys, an LRU cache | scrubbing the top layer recomputes only two layers' tiles; undo hits the cache |
| 3. Pyramid and previews | levels, a coarse-first renderer, slices | the top-layer scrub's preview p95 is within a frame |
| 4. The bench | scenarios, percentiles, exports, gates in CI | every later milestone reports a run against a baseline |
| 5. Workers | tile jobs off the main thread, transferred tiles | input p95 within a frame during refinement |
| 6. WebAssembly kernels | SIMD versions of the costliest kinds (Table 6.1 says which) | three times faster than milestone 5 on those kinds, within tolerance |
| 7. WebGPU executor | residency, fused pointwise passes, staged blurs, display from the GPU, parity tests | the low scrub's full render within a frame on the target GPU |
| 8. Tiers and compression | 16-bit intermediates, checkpoints, disk for pyramids | ten layers of 24 MP within the tablet's budget |

**Table 9.3.** A build order with an exit criterion for each step.

The lab has milestones 1 to 4, with two changes from the table: its cache offers cost-aware eviction as well as LRU, and its bench is closed-loop ([Chapter 7](lab:book?ch=7)). Milestones 6 and 7 exist as probes: the kernels and shaders run and are checked, but the engine does not use them to render. Milestones 5 and 8 are not there. The exercises in Chapters 5 to 8 are, taken together, most of the remaining work.

## 9.11 A worked budget: opening a 24-megapixel document

Table 9.1 asks for a first preview of a ten-layer 24-megapixel document within 500 ms and the full view within 2 s. Can the design meet that, and which milestones does it need? The numbers of Chapters 5 to 8 give an estimate.

A cold render of D-01, eight layers over 614,400 pixels, took 283 ms at 128 px tiles (Table 5.2): 57.6 ms per layer per megapixel. Assume a ten-layer stack costs the same per layer, which is a guess to be replaced by a measurement, and take a 6,000 × 4,000 photograph shown whole in a window 1,500 CSS pixels wide.

| what is rendered | pixels | layer-megapixels | JavaScript, one thread | WebAssembly SIMD at 4.5× |
|---|---|---|---|---|
| level 0, everything | 6,000 × 4,000 | 240 | 13.8 s | 3.1 s |
| the view on a 1× display: level 2 | 1,500 × 1,000 | 15 | 0.86 s | 0.19 s |
| the view on a 2× display: level 1 | 3,000 × 2,000 | 60 | 3.5 s | 0.77 s |
| a first preview one level coarser: level 3 | 750 × 500 | 3.75 | 0.22 s | 0.05 s |

**Table 9.4.** Estimated cold render times for a ten-layer 24-megapixel document, from D-01's measured cost per layer-megapixel and the WebAssembly speed-up of Chapter 8. Estimates, not measurements; decoding and building the source pyramid are not counted.

Three conclusions follow, each checkable once the parts exist.

- **Rendering at the zoom's level is what makes the target reachable at all.** Level 0 would take 13.8 s; the view needs a sixteenth or a quarter of that. This is the exercise of [Chapter 5](lab:book?ch=5) that makes the stage render at the level of Section 5.5, and it is worth more than any later milestone for this requirement.
- **A 2× display breaks the JavaScript engine.** The same window needs four times the pixels, 3.5 s, and fails the 2 s row. WebAssembly at the probe's 4.5 times brings it to 0.77 s; two workers would halve either figure. The first preview passes at level 3 in every column.
- **The estimate is the specification for a measurement.** The 57.6 ms comes from D-01's layers, and a real stack has different ones. The bench scenario that settles the question is a cold open of a 24-megapixel document on the target device, with the gate at 500 ms and 2 s.

## Toward a reusable API

The interfaces between the parts of Figure 9.1, one line each. Each one is something the bench or a test can call.

```text
doc.edit(change) → version                       a new immutable version sharing what the change did not touch
compile(version, view) → jobs                    fused, checkpointed tile jobs with keys, levels and cost estimates
node.describe() → { key, reach, cost, invariant, impls }   what every layer kind declares to the compiler
scheduler.request(version, level, tiles, priority)          newest request per gesture wins; duplicates share a job
executor.run(job) → tile                         gpu, wasm worker or reference, chosen by availability and cost
cache.tier(name).get/put(key, tile)              gpu, cpu and disk tiers, each with a budget and a policy
bench.run(scenarios, profiles) → rows            update p50 and p95, settle, tiles, hit rate, peak memory, gate
parity(executor, reference, kinds) → max error   in 8-bit steps, against the tolerance of Table 9.1
```

## Key points

- State requirements as an event, a measure and a limit, so that a bench can say pass or fail, and repeat runs, because margins move between runs even when verdicts do not.
- Eight production systems agree on four things: rectangular units of work, a separate coarse path, abandoning work only between units, and a slower path that always works.
- They disagree on naming results by content or redrawing invalidated regions, and on fixed or adaptive steps; a browser engine with workers and a long history gains more from content names and fixed tiles.
- Immutable document versions with shared 64 px blocks let several threads render while the person edits, and make undo and keys cheap; Chromium's pending and active trees apply the same idea to the screen.
- Treat the stack as a graph of nodes that declare key, reach, cost, level invariance and implementations, and compile it per render into fused, checkpointed tile jobs, as Halide separates algorithm from schedule.
- A scheduler ranks, coalesces, deduplicates and cancels jobs and hands them to the GPU, WebAssembly workers or the reference.
- Cache by content key in GPU, CPU and disk tiers, each with a budget and a measured eviction policy.
- Build in order: reference, tiles and keys, previews, the bench, workers, WebAssembly, WebGPU, tiers; each step ends with a number.

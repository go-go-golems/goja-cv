# Pyramids and tiles

A 960 × 640 picture has 614,400 pixels, and a stack of eight layers touches each of them eight times. A 24-megapixel photograph has forty times as many. An editor stays responsive by not doing all of that work at once: it divides the picture into **tiles**, so it can redo only the parts that changed, and it keeps the picture at several **resolutions**, so it can show a small version first. This chapter treats both as engineering decisions with costs you can write down, then checks the formulas against the bench and against what Photoshop, darktable, Krita, Halide and Vello chose. By the end you will be able to pick a tile size and an overlap strategy from measurements, choose the pyramid level for a zoom and for a preview, compare downsampling filters by their frequency response, plan a large blur on the pyramid, and say which layers a preview will misrepresent.

## 5.1 The tile grid

The engine renders in tiles, squares of <i>T</i> pixels (128 by default, 64 or 256 from the Bench's Engine block). D-01 at 128 px is a grid of 8 × 5 = 40 tiles; at 64 px it is 15 × 10 = 150. A tile is the unit of three things.

- **Caching.** [Chapter 6](lab:book?ch=6) keys every tile by its content, so an edit recomputes only the tiles whose inputs changed.
- **Scheduling.** [Chapter 7](lab:book?ch=7) renders visible tiles first and stops between tiles when a new edit arrives, so one tile is the smallest step of work the renderer can take.
- **Invalidation for pixels.** A raster records a **revision** for each 64 px block, and a brush stroke raises the revisions of the blocks it touched, so only tiles over those blocks get new keys.

A layer's tile is computed from the tile below it, plus, for a layer with **reach** ([Chapter 4](lab:book?ch=4)), an **apron** of <i>m</i> pixels on every side. The engine computes the region below with the apron, applies the layer, and keeps the middle.

## 5.2 A cost model for the tile size

Smaller tiles waste less work when an edit is small and give the scheduler finer steps. Larger tiles waste less on aprons and on the fixed cost of each tile (looking up keys, allocating a buffer, calling each layer). Three formulas capture the trade, and the bench can test each.

**The apron.** A layer of reach <i>m</i> reads <i>(T + 2m)²</i> pixels to write <i>T²</i>. Table 5.1 gives that ratio for three blurs.

| tile T | σ 1.2 px (m 2) | σ 6 px (m 16) | σ 24 px (m 70) |
|---|---|---|---|
| 64 px | 1.13 × | 2.25 × | 10.16 × |
| 128 px | 1.06 × | 1.56 × | 4.38 × |
| 256 px | 1.03 × | 1.27 × | 2.39 × |

**Table 5.1.** Pixels read per pixel written, <i>((T + 2m) / T)²</i>, for the engine's reach of three Gaussian blurs.

**A local edit.** A brush dab of diameter <i>d</i>, placed at random on a grid of tile size <i>T</i>, overlaps on average <i>(d + T) / T</i> tiles in each direction, so the expected area recomputed is

```math
A(T) = (d + T)²
```

For the bench's 60 px brush: 15,376 pixels at <i>T</i> = 64, 35,344 at 128, and 99,856 at 256, in the ratio 1 : 2.3 : 6.5. Every layer above the painted one recomputes that area, so the ratio carries up the stack.

**The whole picture.** An edit that changes every tile (a slider on a layer near the bottom) recomputes the whole picture whatever the tile size, so only the apron and the fixed cost per tile differ. Larger tiles should win by a little.

## 5.3 Overlap: recompute, store or reread

A layer with reach needs pixels from outside its tile, and an engine has three ways to get them. Ragan-Kelley and colleagues built the Halide language around this choice and describe it as a tension between parallelism, locality and redundant computation. Their example is the smallest pipeline that has the problem: a three-tap horizontal blur followed by a three-tap vertical one, over a 3,072 × 2,048 image.

- **Store everything (breadth first).** Compute the whole first stage, write it to memory, then compute the second stage from it. No value is computed twice, but the intermediate image goes out to memory and comes back, and by the time the second stage needs a row it has long left the processor's cache.
- **Recompute everything (full fusion).** Compute each output pixel straight from the input, recomputing the first-stage values it needs every time. Nothing is stored; their table gives twice the work of breadth first.
- **Tiles with overlap.** For each 32 × 32 output tile, compute the first stage over 34 rows of 32 columns, which fits in cache, then the second stage from that buffer. Only the two extra rows are recomputed, and their table gives 1.0625 times the work. On their x86 machine this schedule ran about ten times faster than breadth first, with the same parallelism.

The tiled number is the apron formula of Section 5.2 in one direction: 34 / 32 = (<i>t</i> + 2<i>m</i>) / <i>t</i> with <i>t</i> = 32 and <i>m</i> = 1. This engine is a fourth point in Halide's space: it stores everything, but per tile. A layer with reach reads the tiles of the layer below that its apron touches, from the cache, and each of those tiles was computed once. For this engine the factor in Figure 5.2 is therefore a factor on reading and copying, not on arithmetic. A fused pass that recomputed the layers below over the apron, which is what a GPU engine does when it fuses (Chapter 8), would pay the factor in arithmetic as well. The price of storing is memory: one cached tile per layer per position ([Chapter 6](lab:book?ch=6)).

Production systems choose a point on the same curve.

- **Photoshop** exposes the choice as a preference with four cache tile sizes. Adobe's guidance is that bigger tiles speed up complex operations such as sharpening filters, while brush strokes and other small changes are more responsive with smaller tiles. That is Figure 5.1 stated as advice.
- **darktable** processes a whole region per module when it fits in memory. When it does not, each module declares how much memory it needs as a multiple of its input (`factor`), its largest single buffer (`maxbuf`), a fixed `overhead` in bytes, and an `overlap` in pixels. The pipeline divides the memory it may use by the factor to get the largest buffer it can afford, and if the region is larger, cuts it into tiles that carry the overlap on every side. A tile at the image edge that would be no wider than twice the overlap is skipped.
- **Deep Zoom pyramids** written by libvips default to 254 px tiles with a one-pixel overlap, so a stored tile is 256 px wide including its borders and a viewer can filter across tile edges without fetching the neighbours.
- **Chromium's compositor** rasterises web content in tiles of about 256 × 256 px in software, and about the viewport's width by a quarter of its height on the GPU, where fewer, larger tiles cost less to manage.

> **Careful.** In this engine the apron depends on the reach of one layer, because every layer's tile is cached. A fused pipeline is different. Fusing <i>k</i> layers of reach <i>m</i> into one pass needs an input apron of <i>k</i> · <i>m</i>, and the factor in Figure 5.2 then applies to the sum: three fused σ 6 px blurs at 128 px tiles read ((128 + 96) / 128)² = 3.06 times the pixels they write.

## 5.4 The pyramid

An **image pyramid** keeps the picture at successive halvings: level 0 is full size, level 1 is half as wide and high, level 2 a quarter. Each level is made from the one below by averaging 2 × 2 blocks, weighted by alpha for the reason in [Chapter 1](lab:book?ch=1):

```js
// engine.js · Raster.prototype.level, the colour average
{{src:Raster.prototype.level:11-13}}
```

Each of the four source pixels adds its colour times its alpha, and the sum is divided by the total alpha; the output alpha is the plain mean. A level costs a quarter of the one below it, so the whole pyramid costs a third more than level 0 alone (<i>1/4 + 1/16 + … = 1/3</i>). Levels are built when first asked for and kept until the raster's revision changes.

Rendering at level <i>L</i> divides the pixel count by <i>4<sup>L</sup></i>. D-01 at level 2 is 240 × 160 px, four 128 px tiles instead of forty. Every layer must render at every level, so the engine passes <i>L</i> to each operation: a blur of <i>σ</i> = 6 px becomes <i>σ</i> = 1.5 px at level 2, and its reach drops from 16 px to 3 px. Vignette, gradients and the geometric mask components of [Chapter 3](lab:book?ch=3) use document coordinates scaled by <i>2<sup>L</sup></i>, so they land in the same place at every level.

## 5.5 Which level to show

There are two different reasons to render at a coarser level, and an engine should keep them apart.

The first is **zoom**. When the view shows the picture at a scale <i>z</i> below 1, each screen pixel covers <i>1/z</i> image pixels in each direction, so level

```math
L = ⌊ log₂ (1 / (z · r)) ⌋
```

(taken as 0 when <i>z · r</i> ≥ 1) already has every pixel the screen can show, where <i>r</i> is the device pixel ratio (2 on most phones and many laptops). A 24-megapixel image shown 1500 px wide on a 2× display has <i>z · r</i> ≈ 0.5, so level 1 is enough and costs a quarter. This is not an approximation: the result is the same picture the screen would show after downsampling level 0, as long as the layers are level-invariant (Section 5.7). The lab renders level 0 at every zoom; the exercises ask you to change that.

Photoshop keeps this structure under the name **cache levels**. Its performance preferences allow up to eight levels of cached image data, four by default, and Adobe's guide says that more levels improve responsiveness while you work at the price of longer loading, and recommends more than four for documents of 50 megapixels or more. The arithmetic explains both halves. Memory is not the cost: levels 1 to 4 add 0.332 of level 0, and levels 1 to 8 add 0.333, so the last four levels cost a thousandth of the picture. Building them is the cost, once per change of a layer's pixels, and the levels pay for themselves only when the view is far enough out to use them. A picture <i>W</i> pixels wide shown whole in a window <i>S</i> device pixels wide needs level ⌊log₂(<i>W</i> / <i>S</i>)⌋: a 50-megapixel frame 8,660 px wide in a 1,500 px window needs level 2, and zooming out to a quarter of that size needs level 4.

The second is **latency**. While a slider moves, a coarser level than the zoom needs is shown on purpose, as a **preview**, and replaced when the gesture ends. [Chapter 7](lab:book?ch=7) describes how the renderer picks the preview level from the time the last one took.

## 5.6 Downsampling, and what it loses

The 2 × 2 average is a **box filter**: cheap, exact for flat areas, and poor at removing detail too fine for the level. A pattern finer than two pixels of the level cannot be represented there; an ideal filter would turn it into an even grey, while the box lets some of it through as a coarser false pattern, which is **aliasing**. The **zone plate** on [the test card](lab:scene?id=D-02), rings whose spacing shrinks outwards, shows where it starts. Better filters remove more of the false pattern and read more: a tent over 4 × 4 pixels reads four times as many as the box, and a Lanczos filter over 12 × 12 reads 36 times as many, or six times when it runs separably, a row pass then a column pass. Because the pyramid is built once per raster revision, a better filter there is cheap; for previews of a changing composite the box is the usual choice.

"Better" can be made exact with a **frequency response**: a filter's gain at frequency <i>f</i>, in cycles per input pixel, is how much of a sinusoid at that frequency survives filtering. Halving the resolution moves the Nyquist limit from 0.5 to 0.25 cycles per input pixel, so whatever survives between 0.25 and 0.5 folds back as a false, coarser pattern. The two-tap average [1, 1] / 2 has gain |cos π<i>f</i>|. Applying it <i>n</i> times gives the **binomial** filters, with gain |cos π<i>f</i>|<sup><i>n</i></sup>:

```math
[1, 1]/2 → |cos πf|,   [1, 2, 1]/4 → cos² πf,   [1, 3, 3, 1]/8 → |cos πf|³,   [1, 4, 6, 4, 1]/16 → cos⁴ πf
```

The box lets 38 % of a pattern at 0.375 cycles per pixel through as aliasing; the five-tap binomial lets 2 % through. The price is paid in the passband: at 0.125 cycles per pixel, detail the halved level can show, the box keeps 0.924 of the contrast, [1, 3, 3, 1] / 8 keeps 0.789 and the five-tap filter 0.729. It is also paid in reads. Run separably, a four-tap filter reads 12 input pixels per output pixel (two half-width row results of four taps each, then four taps down a column) and the five-tap filter 15, against the box's 4.

These are the filters real pyramids use.

- **Williams' mipmap.** The 1983 paper that named the mipmap, from <i>multum in parvo</i>, built each level from the one below with box prefiltering and blended two levels by linear interpolation. Williams called the scheme's most severe compromise its symmetry: a level filters equally in both directions, which wastes detail on a surface seen at a grazing angle. An editor that scales uniformly does not pay that price; a perspective warp does.
- **Burt and Adelson's Gaussian pyramid**, from the same year, built each level with a 5 × 5 weighted average, separable, whose weights depend on one parameter <i>a</i>; at <i>a</i> = 3/8 they are the binomial [1, 4, 6, 4, 1] / 16. Their **Laplacian pyramid** stores the differences between successive levels, which is what local-contrast filters operate on.
- **Halide's local Laplacian filter** and **Vello's CPU renderer** downsample with [1, 3, 3, 1] in each direction (Section 5.8).

Two more properties of the average matter. It is taken over premultiplied values, which is what keeps transparent edges from darkening. And it is taken over sRGB-encoded values, not linear light, so a fine black-and-white pattern averages to sRGB 0.5 (linear 0.21) instead of linear 0.5. A pyramid built in linear light is more correct, and needs either more bits per channel or the decoding cost on every read.

## 5.7 Level invariance

A layer is **level-invariant** when rendering it at level <i>L</i> gives the same result as rendering at level 0 and downsampling, in symbols <i>down(f(x)) = f(down(x))</i>. A preview is only as good as the layers are invariant. Exactly invariant operations are rare: a linear operation on the values that are averaged would be one. Everything else is approximately invariant, and how approximately can be measured. Table 5.3 renders D-01's photograph with one layer at a time, at level 2 and at level 0 averaged down twice, and compares the two in 8-bit steps.

| layer, settings | mean difference | largest | pixels off by more than 4 |
|---|---|---|---|
| (the photograph alone) | 0.15 | 1 | 0.0 % |
| Blur, σ 6 px | 0.12 | 8 | 0.0 % |
| Vignette | 0.20 | 1 | 0.0 % |
| Exposure, +1 EV | 0.40 | 22 | 0.5 % |
| Curves, contrast 0.7 | 0.41 | 17 | 0.7 % |
| Hue and saturation, +60 % | 0.41 | 9 | 0.3 % |
| Sharpen, amount 0.8, σ 1.2 px | 0.46 | 22 | 2.6 % |

| Posterize, 4 levels | 2.80 | 74 | 25.4 % |
| Grain, 8 % | 5.48 | 22 | 56.9 % |

**Table 5.3.** How far a level 2 render of one layer is from the level 0 render averaged down to the same size, on D-01's photograph. Measured by `test/levels.js`.

The pattern follows from the definition. Smooth operations differ only where the picture has fine detail: exposure works in linear light and the pyramid averages sRGB values, so the two disagree most on sharp edges, by up to 22 steps but on half a percent of the pixels. A blur commutes best of all, because a blurred picture has little detail left to lose. Threshold and posterize are step functions, and a step after an average is not an average after a step: wherever a coarse pixel straddles the threshold the two disagree completely. Grain draws one noise value per output pixel, so its level 2 preview has grain four times coarser. A sharpen at level 2 sharpens the detail that level still has, which is less than level 0 had.

For an engine this means: previews of tone and colour layers are safe; previews of step functions and of noise are misleading, and the person should know, either because the preview is marked as one or because the engine renders those layers at level 0 even during a gesture.

## 5.8 Large blurs on the pyramid

Table 5.3 shows that a blur commutes with downsampling better than any other layer, and engines use that to make large blurs cheap. A Gaussian of σ = 100 px needs a kernel of about 6σ + 1 = 601 taps per pass at full resolution, 1,202 reads per pixel for the two passes. Vello's CPU renderer convolves directly only for σ ≤ 2. For larger σ it halves the image several times with the [1, 3, 3, 1] / 8 filter, blurs the small image with a short kernel, and upsamples the result back.

The plan rests on one fact: the variances of successive blurs add. The kernel [1, 3, 3, 1] / 8 sits at offsets ±0.5 and ±1.5 pixels, so its variance is (2 · 1 · 1.5² + 2 · 3 · 0.5²) / 8 = 0.75 square pixels at the resolution it runs at. A decimation at level <i>j</i>, where one pixel spans 2<sup><i>j</i></sup> level 0 pixels, adds 0.75 · 4<sup><i>j</i></sup> in level 0 units, so <i>n</i> decimations together add

```math
v(n) = 0.75 · (1 + 4 + … + 4ⁿ⁻¹) = 0.25 · (4ⁿ − 1)
```

The blur left to do at level <i>n</i> has variance (σ² − <i>v</i>(<i>n</i>)) / 4<sup><i>n</i></sup> in that level's pixels. Table 5.4 works the plan through for σ = 100, with the kernel taken as 2⌈3σ⌉ + 1 taps.

| decimations <i>n</i> | σ so far, level 0 px | σ still to blur, level <i>n</i> px | taps per pass |
|---|---|---|---|
| 0 | 0 | 100.0 | 601 |
| 1 | 0.87 | 50.0 | 301 |
| 2 | 1.94 | 25.0 | 151 |
| 3 | 3.97 | 12.5 | 77 |
| 4 | 7.98 | 6.23 | 39 |
| 5 | 15.99 | 3.09 | 21 |
| 6 | 32.0 | 1.48 | 11 |

**Table 5.4.** A pyramid plan for a Gaussian blur of σ = 100 px, from <i>v</i>(<i>n</i>) = 0.25 · (4<sup><i>n</i></sup> − 1). Computed, not measured.

Vello's source, read for this chapter, plans σ = 100 as six decimations and an 11-tap kernel, which is the last row. The work falls from 1,202 reads per output pixel to about four for the six decimations (12 reads per pixel of each smaller level, and the levels shrink by four), 0.005 for the blur at level 6, and about as much again as the decimations for the upsampling: two orders of magnitude.

> **Careful.** The upsampling filters blur as well, and the arithmetic above leaves them out, so a plan that ignores them overshoots σ slightly. And in a tiled engine the pyramid shortens the arithmetic, not the apron: a σ = 100 blur still needs about 3σ = 300 px of input around each tile, whichever method runs inside the apron.

This engine applies the same variance reasoning in one place already: a blur rendered at level <i>L</i> uses σ / 2<sup><i>L</i></sup> (Section 5.4). It does not yet use the pyramid inside a full-resolution blur; the exercises ask for it.

> **Exercise.** Plan σ = 30 px with the rule above. How many decimations bring the kernel under 15 taps, and what is the cost in reads per output pixel against the direct blur?

## 5.9 Previews in other engines

The lab's preview renders the whole stack at a coarser level. Other editors draw the same distinction in different places.

- **Krita** calls its version **Instant Preview**; it was funded by the 2015 Kickstarter and was first known as level-of-detail strokes. It draws a stroke's feedback on a smaller version of the canvas while the full stroke is computed in the background. Its documentation states the two limits this chapter predicts. A brush setting whose coarse result would differ from the real one turns Instant Preview off for that brush: the colour smudge brush's overlay mode and a size driven by the fade sensor are its examples, which is level invariance (Section 5.7) applied to brushes. And a 4K image at 100 % zoom on a 4K screen gains nothing, because the smaller canvas would have to be level 0. Krita's developers also noted that once a coarse stroke has started, the full one cannot take over midway: it has to be computed from the beginning, so the coarse preview is extra work, not a head start.
- **darktable** runs a separate **preview pipe** next to the full one. The preview pipe processes a small copy of the image for the navigation thumbnail and the histogram, with a cache of 12 lines against the full pipe's 64 ([Chapter 6](lab:book?ch=6)).
- **Photoshop** draws from its cache levels (Section 5.5), so a zoomed-out view is composed from a coarse level, never from level 0.

The lab's design is closest to Krita's, applied to every layer rather than to a brush.

> **Try it.** With the [tile overlay](lab:overlay?name=tiles) on, [select Contrast](lab:select?layer=Contrast) and move its contrast slider, then [Vignette](lab:select?layer=Vignette). Count the red outlines after each. Then [set the tile size to 64 px](lab:tile?size=64), paint a short stroke on Paint, and [run the stroke scenario at all three tile sizes](lab:bench?scenario=stroke-low&profile=here&tile=64,128,256&preview=off&evict=lru&run=1).

Table 5.2 came from one machine. The program below measures it on yours: every render starts from a fresh copy of the document with an empty cache, so each number is a cold render, and the median of three is kept.

```run tile-sizes.js
// Cold renders of this document at three tile sizes and three pyramid levels. Each render uses a
// fresh copy of the document with its own cache, so nothing is warm. Median of three; compare Table 5.2.
const rows = [];
for (const tile of [64, 128, 256]) for (const L of [0, 1, 2]) {
  const ms = [];
  let tiles = 0;
  for (let r = 0; r < 3; r++) {
    const ws = new Workspace(cloneDoc(app.ws.doc), { tile, budgetMB: 512 }), g = ws.engine.grid(L);
    const t0 = performance.now(); ws.composite(L); ms.push(performance.now() - t0); tiles = g.nx * g.ny;
  }
  rows.push({ tile, level: L, tiles, ms: +ms.sort((a, b) => a - b)[1].toFixed(1) });
}
return rows;
```

Read the result against two predictions from this chapter: each level down should cost a quarter of the one above or a little more, and at level 0 the 64 px grid should be the slowest of the three.

## Toward a reusable API

The mechanisms of this chapter reduce to a few functions with one-line meanings. An engine that has them can be tested against the formulas above.

```text
grid(L) → { w, h, nx, ny }                     the tile grid at pyramid level L
tileRect(L, tx, ty) → { x, y, w, h }           a tile's pixels, clipped at the picture's edge
reach(layer, L) → m                            pixels of apron the layer reads at level L
apronFactor(t, m) → ((t + 2m) / t)²            pixels read per pixel written; recomputation when fused
zoomLevel(z, r) → max(0, ⌊log₂(1 / (z · r))⌋)  the level whose pixels a zoom z shows at device ratio r
downsample(level, filter) → next level         premultiplied; filter is box, [1,3,3,1]/8 or [1,4,6,4,1]/16
blurPlan(σ) → { decimations, σ_rest, taps }    the pyramid plan of Table 5.4
invariance(kind, L) → { mean, max, over4 }     the measured preview error of Table 5.3
```

## Key points

- Tiles are the unit of caching, scheduling and pixel invalidation, so the tile size is a trade between wasted work on small edits and fixed cost per tile.
- A local edit of size <i>d</i> recomputes about (<i>d</i> + <i>t</i>)² pixels per layer, and a layer of reach <i>m</i> reads (<i>t</i> + 2<i>m</i>)² per tile; small tiles suit painting and large ones suit long reach, which is also Adobe's advice for Photoshop.
- Pixels beyond a tile can be stored, recomputed or reread; Halide measured overlapped tiles at 1.0625 times the work and about ten times the speed of storing a whole intermediate.
- This engine stores every layer per tile, so its apron costs reads, not arithmetic; a fused pass pays the apron of every fused layer in arithmetic.
- A pyramid level costs a quarter of the one below, all levels together a third of level 0, and in practice each level down buys a factor of three to four.
- Choose the zoom level from <i>z</i> · <i>r</i>, and a coarser level only as a preview.
- Binomial filters [1, 3, 3, 1] / 8 and [1, 4, 6, 4, 1] / 16 pass 6 % and 2 % of the aliasing band's middle where the box passes 38 %, for three to four times the reads.
- Variances add, so a large blur can run as a few decimations and a short kernel: σ = 100 px becomes six decimations and 11 taps.
- A layer is level-invariant if downsampling commutes with it; tone and colour layers nearly are, while thresholds, posterize and grain are not, and Krita disables its previews for brush settings of the second kind.

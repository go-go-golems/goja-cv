Summary
The Editor lab is a photo-editing workbench that runs as one HTML page: a tiled, content-
cached engine, a stage with ten tools, an agent and a code editor that drive the same API,
a benchmark bench, 32 presets and a nine-chapter textbook. It is published as Editor lab
(version 1794686042-0718, 14 November 2026, 19:54 UTC), and the zip that goes with this
report holds its full source, tools, tests, research notes and screenshots.
State at handoff:
Every test suite passed on the last build, and the book checker reports no errors in
any of the nine chapters.
The last request, layer grouping with metadata that links layers back to the code or
preset that made them, was interrupted before any work started (see Not done).
The engine renders in JavaScript on the main thread. WebAssembly and WebGPU
exist as probes that are checked against the engine, not yet as render paths.

Architecture
Everything runs in one page: a document model, a tile engine that names every tile by a
hash of its inputs, a renderer that shows a coarse preview first, and nine views that all
reach the document through the same lab API. build.py concatenates 17 scripts, the
book and the WebAssembly kernels into index.html.
Editor lab architecture · 5 views, one API, 3 core parts
Every view acts on the document only through the lab API. The Workspace records each
change, Render asks the Engine for a preview and then for level 0 tiles, and the probes are
checked against the Engine's output.
How an edit reaches the screen:
1. A tool, a slider, the agent or a program changes the Workspace (layers, masks, pixels),
which records a command in history.
2. Render.request asks for a coarse preview at once and queues the level 0 tiles, visible
ones first and nearest the middle.
Page 6 of 19

3. For each tile, Engine.key hashes the layer's settings, the pixel revisions it reads and
the keys of the tiles below it into a 52-bit key. A key found in the TileCache costs
nothing; a missing one is computed by applyLayer from the tile below plus its apron.
4. The refining loop runs at most 8 ms of tiles per frame and abandons the queue
between tiles when a newer edit arrives.

Findings that are the book's own, each checkable from the zip:
The lab and darktable both use deep constructive traces. Each key is built from the
keys below, so a lookup needs no pixels but a rebuild can never stop early.
On D-01 that wastes up to half the work. After an edit, Darker sky leaves 16 of 40
output tiles bit-identical and Sun glow 26 of 40, so 33 % and 52 % of the tile
computations above them are avoidable; Contrast leaves none ( test/cutoff.js).
Two fixes, priced. A zero mask over a tile lets the key pass through, as a hidden layer's
does, for one rectangle test. Hashing output tiles costs 0.093 ms for a 128 px float tile,
15 to 22 % of a cheap layer's tile.
GIMP's adaptive chunks overshoot twice. A port of its rule shows two 266 ms chunks
after the cost per pixel quadruples, because the median of three aims lags one step
more than the newest aim would.
Vello's blur plan follows from adding variances. Six decimations with [1, 3, 3, 1]/8 and
an 11-tap kernel reproduce its plan for σ = 100, at about 1 % of the direct blur's reads.
Adobe's tile advice matches the bench. Bigger tiles for sharpening and smaller for
strokes is what Figure 5.1 measured: strokes run 1 : 2.4 : 5.8 at 64, 128 and 256 px, and a
large blur 3.5 times slower at 64 px than at 256.
The 24-megapixel open is reachable only with zoom-level rendering. Estimated from
D-01's cost per layer-megapixel, level 0 takes 13.8 s, the view on a 2× display 3.5 s in
JavaScript and 0.77 s with WebAssembly SIMD.

Not done, open items and known limits
The biggest open item is the interrupted request for layer groups with provenance; after
it come the engine milestones the book names but the lab does not have.
Layer grouping and provenance (requested, not started). It fits the existing design in
three parts:
A group layer kind whose children render into their own tile stack and blend as one
layer, either isolated or passing through; its key hashes its settings and the keys of its
children's top tiles, so the content cache needs no change.
A meta record on every layer and group: what made it (a built-in preset, a saved
preset, a program file and line, an agent step, a tool), with the id that finds it again.
Presets.apply, the Code view's runner, code layers and the agent's eval would
stamp it.
In Layers and Params, a link from that record that opens the preset or the program in
the Code view at the right line, and the reverse: a program that lists the layers it made
on the stage.
Engine milestones not built (Chapter 9's build order):
No workers: everything renders on the main thread (milestone 5).
WebAssembly and WebGPU run only as probes checked against the engine, not as
render paths (milestones 6 and 7).
No cache tiers or 16-bit storage (milestone 8).
The stage renders level 0 at every zoom; rendering at the zoom's level is a Chapter 5
exercise and the step that most improves the 24-megapixel estimate.
Early cutoff through zero-mask pass-through is described and priced but not
implemented.
